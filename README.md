# Visitor Management App (Flutter + BLoC)

## Features
- Dashboard metrics calculated from visitor records using the device's local date.
- Visitor registration and editing with name, exactly 10-digit mobile, optional validated email, visitor type, project and purpose.
- Visitor list, search by name/mobile, details, delete confirmation.
- QR code generation using the server-returned visitor ID and camera-based QR scanning.
- Check-in/check-out timestamps and workflow restrictions.
- REST GET, GET-by-ID, POST, PUT and DELETE through Dio, with loading/error feedback.
- BLoC events/states for shared visitor data and dashboard/list updates.

## Setup
1. Install Flutter and Android SDK, then run `flutter doctor`.
2. Create a persistent MockAPI resource named `visitors` with the fields in the assignment.
3. Update `lib/core/config/api_config.dart` so `visitorsBaseUrl` is the full URL of that resource, for example `https://YOUR_PROJECT.mockapi.io/api/v1/visitors`.
4. From the project folder run:
   ```bash
   flutter pub get
   flutter run
   ```
5. Android camera permission is requested by the scanner package. If camera access is denied, allow it in Android settings.
6. Build APK: `flutter build apk --release`. The output is `build/app/outputs/flutter-apk/app-release.apk`.

## State management
BLoC separates user actions (events) from renderable states. `VisitorBloc` coordinates API calls through `VisitorRepository`; screens listen to the same BLoC so changes are reflected in dashboard and list without restarting.

## API contract
Base URL must point directly to the `/visitors` resource. Supported operations:
- `GET /visitors`
- `GET /visitors/{id}`
- `POST /visitors`
- `PUT /visitors/{id}`
- `DELETE /visitors/{id}`

The API must return the created visitor's server-generated `id`. Data keys follow the assignment's snake_case JSON (`visitor_type`, `created_at`, `check_in_time`, `check_out_time`).


Release builds are signed with the Flutter debug signing configuration until a proper release signing key is configured (no signing credentials are stored in the repository).

## GitHub Actions CI/CD
The workflow in `.github/workflows/flutter-ci-cd.yml` runs on pushes to `main`/`master`, pull requests targeting `main`/`master`, and manual dispatch. On every run it:
1. Checks out the repository.
2. Sets up Java 17.
3. Installs a stable Flutter SDK.
4. Runs `flutter pub get`.
5. Runs `flutter analyze`.
6. Runs `flutter test`.
7. Builds the release APK with `flutter build apk --release`.
8. Verifies `build/app/outputs/flutter-apk/app-release.apk` exists.
9. Uploads the APK as the `visitor-management-release-apk` artifact (7-day retention).

The APK artifact can be downloaded from the GitHub Actions run page under the "Artifacts" section.

### Android camera permission
If your generated `android/app/src/main/AndroidManifest.xml` does not already declare camera access, add this directly under the `<manifest>` element:
```xml
<uses-permission android:name="android.permission.CAMERA" />
```
The release manifest also declares `android.permission.INTERNET`, which is required for the release APK to reach the visitor API.
